# Project context

Prep Tracker — a local-first, spaced-repetition interview-prep tracker. See `README.md` for the product overview.

## Architecture (read before changing data flow)

- **Local-first.** The client reads from an in-memory store (`lib/store/store.ts`, via `useSyncExternalStore`) hydrated from IndexedDB (`lib/store/idb.ts`). Components read the store, not the network. Prefer optimistic writes: mutate the store first, sync in the background, roll back on error (see `lib/store/writeQueue.ts`).

  **The offline queue is at-least-once, so every queued write carries an idempotency key.** A send whose response is lost gets resent, so each queued attempt mints a `client_id` when logged and reuses it on every retry; `attempts.client_id` is UNIQUE and the POST answers a repeat key with the stored row (200) instead of a second insert — which would also step the card's level twice. Three more rules keep the queue whole: change it only through `updateQueue()` (a Web Lock — two unserialised read-modify-writes of the one IndexedDB array lose an entry), flush only through `flushQueue()` (single-flight, so two loops never send the same head), and only a retryable status (`isRetryableStatus()`: 5xx, 401/403, 408/429) stops the flush — any other 4xx is set aside under `writeQueueRejected`, or it would block everything behind it forever. A server write that reads history and writes state derived from it (an attempt plus the replayed level) goes in one `writeTransaction()` (`lib/db.ts`).
- **Sync.** `GET /api/sync` returns the full dataset; the client persists it to IndexedDB. Server is libSQL/Turso (`lib/db.ts`, needs `TURSO_DATABASE_URL`).
- **Pure logic lives in `lib/`** and is unit-tested: `sr.ts` (scheduler), `practice.ts`, `streak.ts`, `cardTags.ts`, `store/queries.ts`, `useSwipeNav.ts`, `auth.ts`, `rateLimit.ts`. Keep new logic pure and testable there.
- **A practice set is a spec, not a mode** (`lib/practice.ts`). A `PracticeSpec` is data on three independent axes — scope (`due` / `weak` / `all` / `unattempted`), order, size — plus domain/proficiency/field filters, so the global review queue and a per-domain session (`/{domain}/review`) run through one code path. A new way to practice is a new spec, not a fork of the session page. The invariant that keeps existing `?order=` links working is asserted in `practice.test.ts`: for any `scope: 'due'` spec, `buildPracticeSet` returns exactly `reviewQueue(...)` filtered by domain and proficiency.
- **Archiving a domain hides it everywhere but Settings, without touching the data.** `archivedDomainIds()` (`lib/domains.ts`) is the one rule. Two things apply it:
  - **Rotation** — `reviewQueue()` and `forecast()` (`lib/store/queries.ts`) and `buildPracticeSet()` (`lib/practice.ts`) skip those cards, so an archived domain leaves the queue, the badges, the forecast and every practice set, including its own launcher. Both admission points must apply the rule, or the `scope: 'due'` equivalence above breaks.
  - **Aggregates** — `activeCards()` (`lib/store/queries.ts`) is the same rule as a card/attempt filter, and `historyBuckets()`, `activityDays()`, `todayStats()` and `computeMetrics()` (`lib/store/metrics.ts`) all read it instead of `data.problems`/`data.attempts`. So an archived deck contributes no row, chip, percentage or study day to Today's History or Stats either — recall rate, streak, heatmap, proficiency split and leeches included. Components list `activeDomains()`, never `allDomains()` (which is Settings-only), so an empty archived domain can't sit in a domain-ordered list as a "0 added" placeholder.

  Nothing is deleted: cards, due dates and attempt history are untouched and every number comes straight back on restore. `/{slug}` still renders an archived domain's cards read-only for anyone who has the URL — it just isn't linked from anywhere.
- **History is a day view, not a "today" view.** Attempts are never pruned (`/api/sync` is a bare `SELECT * FROM attempts`), so every day you have ever studied is browsable. `/review/history` takes the day from `?date=` — `resolveHistoryDate()` in `lib/historyDay.ts` resolves it, clamping the future and falling back to today — and passes it to `historyBuckets(data, date, …)`, which was always date-parameterized. The arrows step **one calendar day at a time over every day, empty ones included** (`adjacentDay()`) — a day you logged nothing is part of your history and skipping it hides the gap. They are bounded, not filtered: forward stops at today, backward stops at `activityDays()[0]`, your first logged day, since everything before that is empty by definition. `activityDays()` is *not* an arrow whitelist; its other use is the "jump to the last session before this" link on an empty day, via `adjacentActivityDay()`. Don't reintroduce a `clientToday()` call inside the page — the day comes from the URL, which is what makes a history link shareable and the back button work.
- **Theming is token-driven.** Colors are CSS variables in `app/globals.css` (`:root` light, `.dark` dark); components use semantic classes (`bg-surface`, `text-accent`, …). Change tokens, not per-component hex. Both light and dark must work. Each block also sets `color-scheme`, which is what native controls (date inputs, scrollbars) draw themselves from — they ignore the tokens.

  **The theme *preference* is three-state; the *resolved* theme is two.** `lib/theme.ts` holds the split: `localStorage.theme` stores `'light' | 'dark' | 'system'`, and `resolveTheme()` turns that into the `dark` class using `prefers-color-scheme`. Storing 'system' as itself — rather than as whatever the OS said when you picked it — is what lets `ThemeToggle` subscribe to the media query and follow the OS mid-session; an explicit light/dark must keep ignoring it, so that listener is scoped to 'system'. An unrecognised or absent stored value reads as 'system', which is what the app already did before the preference existed, so nobody's setting changes on upgrade. The pre-paint boot script in `app/layout.tsx` necessarily *restates* this resolution in ES5 (it runs before any bundle), but it interpolates the colors and the storage key from `lib/theme.ts` so the values can't drift — if the resolution rule changes, change both.
- **Auth.** `proxy.ts` (Next 16's name for middleware) gates everything except `/login`, `/api/auth`, and static/PWA assets when `AUTH_SECRET` is set (fail-open otherwise). The decision itself is the pure `decideRoute()` in `lib/routing.ts`, unit-tested as a table — change it there, not in the proxy. After sign-in, `safeNextPath()` only follows a same-site path.

  **Sign-in is Cognito managed login; the session is the app's own.** `/api/auth/login` starts the authorization code flow with PKCE, `state` and `nonce`, carried in a 10-minute signed `pt_oauth` cookie (`signToken()` in `lib/auth.ts`); `/api/auth/callback` checks the state against it, exchanges the code on the server with the client secret, verifies the ID token with `aws-jwt-verify` plus the nonce (`lib/oidc.ts`), and mints `pt_auth` naming the app user. Cognito's tokens aren't kept. `resolveUser()` (`lib/accounts.ts`) picks that user: the one linked to the Cognito `sub`; else one waiting with that **verified** email (the owner and imported accounts get an email ahead of their first sign-in); else a new `usr_<uuid>` with the seven starter decks, empty. Redirect URIs come from `SITE_URL`, never the request's Host — behind CloudFront the Lambda sees its own host. The user pool, its managed-login domain and branding, and the confidential app client are `cognito()` in `sst.config.ts`; each stage needs its `SiteUrl` secret set before deploying, since the callback URLs are built from it. **The passcode is local-only**: with no Cognito settings (`cognitoConfig()` returns null) `/login` shows the passcode form, which mints the owner's session for `npm run dev` and the e2e suite; no deployed stage sets `APP_PASSWORD`. Signing out ends at `/api/auth/logout`, which clears `pt_auth` and ends the Cognito session too. `withUser()` also refuses a session whose user is deleted or unknown, so `DELETE /api/account` (`lib/accountData.ts`: every row, then the Cognito user) signs that account out on every device; `GET /api/account` is the data export.

  **Signed out, `/` is the landing page** (`app/(public)/welcome/page.tsx`), rewritten in place so the shared link stays bare; any other page redirects to `/?next=…`, whose Sign in carries `next` on to `/login`. The rewrite sets `x-prep-public: 1`, and both the service worker and `RegisterSW`'s warm-up skip caching such a response — a cached landing page under `/` would later open, offline, instead of the signed-in queue. Its screenshots come from the demo via `npm run screenshots` (`scripts/screenshots.mjs`); re-run it after a visible UI change.

  **Two route groups, one shell.** `app/(app)/` holds every signed-in page and its `layout.tsx` mounts the shell: `StoreProvider` (and so the store, its sync and the banner), `RegisterSW`, `Nav`, the shortcuts. `app/(public)/` (login, and the landing page) gets none of it, so a signed-out visitor never boots the store or calls `/api/sync`. A page that needs the store belongs in `(app)`.

  **Signing out assumes a shared device** (`lib/store/signOut.ts`), in a fixed order: upload the offline queue, end the session, *then* wipe what the browser holds — every account's IndexedDB database on the device (`idbDestroyAllAccounts()`, which also blocks any later write from that page) and every service-worker cache but the hashed `assets-*` bundles. It refuses offline, keeps local data if the server can't end the session, and discards reviews that still won't upload only after asking. Other tabs hear it on a `BroadcastChannel` and follow. Anything new the browser stores per account must live in IndexedDB or a non-`assets-` cache, or be added to `wipeLocalData()` — otherwise it survives sign-out for the next person.

  **Each account has its own IndexedDB database**, `prep-store-<userId>` (`lib/store/localAccount.ts`), named from the readable `pt_user` cookie that every session sets beside the httpOnly `pt_auth` (`lib/sessionCookies.ts` sets and clears the pair — use it, never one cookie alone). The hint only picks a database; the server trusts nothing but the signed token. On boot, `claimLocalData()` runs before anything reads the store: another account's database on the device is deleted (a session can end without a sign-out — expiry, or deletion elsewhere — and the next person must not see, or upload, the last one's data), and the pre-accounts `prep-store` is moved into the owner's database, queue included, or deleted if anyone else signed in. The name is fixed for a page's life, so a hint `/api/sync` sets mid-page (it heals sessions from before the hint) takes effect on the next load. **The service worker doesn't cache `/api/sync`**: Cache Storage is keyed by URL alone, so it would hand one account's data to the next offline; IndexedDB already holds it.

- **Every row belongs to one user, and a route only ever touches the signed-in user's.** The per-user tables (`USER_TABLES` in `scripts/migrate-domains.mjs`: domains, fields, options, config options, problems, attempts, notes, links, study plans, plan tasks) each carry `user_id`; rows from before accounts belong to `usr_owner` (`OWNER_USER_ID` in `lib/auth.ts`). The column is nullable — SQLite can't add NOT NULL without rebuilding the table, and rebuilding `problems` under `ON DELETE CASCADE` risks its attempts — so triggers enforce it: an insert without a `user_id` aborts, and a row can't change hands. The rules for a route:
  - **Wrap it in `withUser()`** (`lib/currentUser.ts`). The user comes from the session cookie (`readSession()`, whose token carries `uid`; a token from before that is the owner's), never from the body or URL. With auth off there is only the owner.
  - **Every query filters on `user_id`**, including lookups by id and the `lib/domain-server.ts` helpers, which all take `userId` first. A child row (note, link, attempt, field, option) is written only after its parent is confirmed the caller's — `INSERT … SELECT … FROM problems WHERE id = ? AND user_id = ?` does both at once.
  - **Someone else's row is a 404**, the same as a missing one, so a response never reveals that it exists. Deletes stay idempotent instead (200 whether or not a row matched) — an offline-queue retry of a delete that landed must succeed — and the scoping alone keeps them to the caller's rows.
  - **Uniqueness is per user**: slugs (`UNIQUE(user_id, lower(slug))`) and the offline queue's key (`UNIQUE(user_id, client_id)`, so one user's retry key can never hand back another's attempt).

  `app/api/access.test.ts` is the proof: it calls every route as user B against user A's rows on a real migrated database and asserts B reads, changes and attaches to nothing of A's. It also lists every route file, so **a new route fails CI until it has a case there** (or a reason in `NO_USER_DATA`). A new per-user table goes in `USER_TABLES` and in that test.
- **Telemetry: traces to Grafana Cloud, product events to PostHog — both off until configured, and neither may carry card text.**
  - **Tracing** (`instrumentation.ts`, `lib/telemetry.ts`): an OTLP/HTTP exporter is registered only when `OTEL_EXPORTER_OTLP_ENDPOINT` is a URL (the `OtelEndpoint`/`OtelHeaders` stage secrets; `'off'` by default), so tests, e2e and `npm run dev` load nothing. Next.js traces requests and renders itself; on top, every Turso round trip and write transaction is a span (`lib/db.ts`: statement text, never values), and API requests carry `enduser.id` (the internal id, never the email), `faas.coldstart` and, for `/api/sync`, row counts and payload size. **Lambda freezes once a response is sent**, so `withUser()` flushes after each API response (capped at 1.5 s); a page render's spans go out with the next API call, which every page load makes. The flush hook lives on `globalThis` because `instrumentation.ts` is bundled apart from the routes — a module-level variable wouldn't be shared.
  - **Analytics** (`lib/analytics.ts`): PostHog, only when `NEXT_PUBLIC_POSTHOG_KEY` is set at build, loaded on demand. **Autocapture and session replay stay off** — both would record card text off the page. Page views plus the named events in `AnalyticsEvent` only (counts and flags); a new event goes in that union. A person is their `pt_user` id; `wipeLocalData()` resets it; the demo is tagged `demo: true`. Events post to this site's `/ingest`, rewritten to PostHog in `next.config.ts` (and outside the proxy's matcher, so the signed-out landing page counts too).
- **The demo dataset is generated, never stored** (`lib/demo/`). `cards.ts` is the deck — 40 cards (DSA, System Design, AWS; no Behavioral), in the house style and in original wording, since it ships to anyone who opens the demo. `buildDemoDataset(now)` replays ~100 days of a simulated learner from a fixed seed, relative to the visitor's own clock, so there is always a queue due today and a live streak; every level and due date comes from `replaySchedule`. It is the **one** place synthetic attempts are allowed — the seeding rule below forbids them for real decks, and this data never reaches a server. `dataset.test.ts` pins its shape (every proficiency level present, a small overdue backlog, ~75% recall) across dates; if a change breaks those, re-pick `DEMO_SEED` rather than loosening the test.

- **Demo mode: the same app, no network writes** (`lib/demo/mode.ts`). `/demo` sets the `pt_demo` cookie, `/demo/exit` clears it; `isDemo()` reads it. In demo mode: the store boots from `buildDemoDataset()` (kept up to 7 days, then rebuilt) instead of `/api/sync`; IndexedDB is a separate database, `prep-store-demo`, so a demo never touches an account's cache or queue (and boot cleanup leaves it alone); `flushQueue`, `syncNow` and the attempt edit/delete calls change the store and stop; notes are store-only (`demoNote()`); and the content-editing screens (`/[slug]/log`, `/log`, `/[slug]/[id]/edit`, `/settings`) render `DemoGate` instead. Behind all that, `installDemoFetchGuard()` turns any `/api/*` request into a local 403, and the proxy never grants `/api/*` to a demo cookie (anyone can set it). **A new server write must check `isDemo()`** — keep the change in the store and skip the request, or gate the screen.

## Scripts (`scripts/`)

Deliberately small — it is not an archive. Everything in it is either live or
wired to an npm script.

**The seeds are local-only.** `scripts/seed-*.mjs`, `scripts/*-cards.md` and
one-off card repairs (`scripts/fix-*.mjs`) are gitignored and not published —
they exist on the authoring machine, not on GitHub. They are still the workflow
described below; they just aren't in the repo, so treat the DB as the only
shared copy of the card text and don't expect a clone to have them.

- **`seed-aws.mjs` + `aws-cards.md`** — the live card-authoring workflow. `aws-cards.md` is the source of truth for the AWS deck's questions and answers: edit there, not in the app, or the next run overwrites the edit. The script is incremental and idempotent (domain/fields/options reused, cards matched on exact question text). Its header also codifies the **house card style** — one card one fact, 250–450 character answers, answer first — which applies to every deck, not just AWS.
- **`seed-behavioral.mjs` + `behavioral-cards.md`** — the same live workflow for the **Behavioral** deck, one section per Hello Interview course article. Differences from the AWS pair: it never creates the domain or its fields (`behavioral` already has them, so a missing one is an error), each `## Category` section declares its source article with a `Link:` line that becomes a per-card `links` row labelled with the card's own question, and `--dry` parses and prints without writing — use it to review a batch before it lands. `behavioral-cards.md` currently covers only the `Practice` section; the older 74 cards predate the file and live only in the DB, so the orphan check is scoped to the categories the file actually covers.
- **`seed-system-design.mjs` + `system-design-cards.md`** — the same live workflow for the **System Design** deck, with the Behavioral pair's contract (existing domain and fields required, per-card article `links`, `--dry`, orphan check scoped to covered topics). Differences: each section is `## <sd_topic>` plus a `Bucket:` line giving its `sd_category`, because a bucket spans many topics; a card may add an `Anchor: <slug>` line between Q and A to deep-link into its article; `---` is a horizontal rule inside an answer, not a card separator; and section order sets the Topic/Bucket dropdown order in the app. It writes both `metadata_json` and the legacy `sd_category`/`sd_topic` columns.
- **`seed-lld.mjs` + `lld-cards.md`** — the same live workflow for the **Low-Level Design** deck, with the System Design pair's format (`## Topic`, `Bucket:`, `Link:`, optional `Anchor:`). The one difference: topic names are not unique in this deck ("Introduction" sits under two buckets), so each `## ` heading opens a new section instead of being keyed by its text.
- **`migrate-domains.mjs`** (+ `migrate-domains.test.ts`) — the whole schema, as migrations: the core tables, the runtime-domain registry, the `attempts.client_id` idempotency key, the study plan tables and accounts (`users`, `user_id` everywhere), wired to `npm run db:migrate`. It is the only way a database gets its tables — nothing creates them at runtime — so a fresh database is one `db:migrate` away from working, and a schema change goes here or a new deployment never gets it. Each migration runs once: it's recorded in `schema_migrations` and skipped on every later run, because re-running a data migration overwrites what Settings has changed since. Add a new entry to the `migrations` list; never edit one that has been applied.
- **`import-user.mjs`** (+ `import-user.test.ts`) — imports another copy of the app's database as one new user of this one, wired to `npm run db:import-user`. It exists to bring Rida's copy (`rida-prep-tracker-bom`, a fork with GRE/TOEFL decks and a study plan) into the shared database. Every row gets fresh ids and the new `user_id`, legacy-column values the target has no column for are folded into `metadata_json`, empty `e2e-domain-*` decks are skipped, and the whole import is one write transaction; it refuses a user id that already exists. It takes its source and target only from `SOURCE_*` / `TARGET_*` env vars and never reads `.env.local`, whose database is production. Run `--dry` first. **Delete it once the import has been applied to production.**
- **`smoke.mjs`** — the post-deploy smoke test, wired to `npm run smoke` and run by `deploy-stage.yml` (see CI/CD below).
- **`screenshots.mjs`** — captures the landing page's screenshots from the demo against a running production build, wired to `npm run screenshots`.
- **`geticon.mjs`** — icon helper.

Conventions for anything you add here:

- **A one-off seed or repair script is deleted once it has been applied.** These write straight to Turso, so a spent script does nothing useful on a re-run and a stale one is a hazard. The card text lives in the DB, so run it, then delete it. A gitignored script (any `seed-*` or `fix-*`) never reaches git, so once deleted it is gone — the DB is the record. Don't grow a graveyard of past seeds.
- **Seed a new card due tomorrow, with zero attempts — never fake a first attempt.** Insert with `interval_level 0` and `next_due_date` = the day after it was added (level 0's interval, `dueDateFor(0)` in `lib/sr.ts`) and stop there. That is what makes a card you add today appear in the Review Queue tomorrow: `reviewQueue()` in `lib/store/queries.ts` admits on the due date alone — a prior attempt is *not* required — and `matchesScope`'s `'due'` branch in `lib/practice.ts` restates the same rule. Writing a synthetic "got it" attempt to force a card into the queue backfires twice: `computeStreak` counts the seed run as a study day, and the **Resume** preset (`scope: 'unattempted'`, `order: 'oldest'`, see `app/(app)/[domainSlug]/review/page.tsx`) means *strictly* zero attempts, so it then skips the exact cards it exists to surface. A card left with `next_due_date NULL` is never scheduled and reachable only through Resume — that is the right state for a bulk import you don't want dropped into the queue at once.
- Scripts read Turso credentials from `.env.local`; they are plain `node` (no build step).

## Conventions

- Dev server runs on **port 3007** (`npm run dev`).
- Verify changes: `npx tsc --noEmit`, `npm test` (Vitest), `npm run test:e2e` (Playwright). Add unit tests for new pure logic.
- **The e2e suite runs on its own server and database, never `.env.local`'s** (which is production). `e2e/server.mjs` builds a fresh `e2e/.tmp/e2e.db` with the real migration, seeds two accounts (`e2e/env.mjs`), and starts `next dev` on port 3017 with its own build folder (`NEXT_DIST_DIR=.next-e2e`), so it runs beside `npm run dev` and is never reused. Its throwaway passcode can sign in as a chosen user (`{ password, user_id }` to `/api/auth`) only with `ALLOW_SIGN_IN_AS=1`, which nothing but that server sets, and never in a production build. `e2e/accounts.spec.ts` uses it for the two-account tests: separate data, a second account on the same browser, sign-out leaving nothing.
- **CI/CD** (`.github/workflows/`): `ci.yml` runs types, unit and e2e on every push and PR. `deploy.yml` on main runs those checks, then `deploy-stage.yml` for staging: migrate the stage's database, `sst deploy`, `npm run smoke` (`scripts/smoke.mjs`), and move the `deployed/<stage>` tag to the commit; a failed smoke test redeploys the commit that tag points at. Production is a manual run (`workflow_dispatch`, stage production) until the switch-over. AWS access is OIDC to `prep-tracker-github-deploy` (the `ci` stage of `sst.config.ts`, deployed once by hand), which trusts only jobs in the `aws-staging` / `aws-production` GitHub environments — named so to stay clear of Vercel's own `Preview`/`Production`. CI reads each stage's settings from its SST secrets; nothing is stored in GitHub but the role ARN and the public `NEXT_PUBLIC_*` values, as repository variables.
- **The smoke test runs as `usr_smoke`**, an account `scripts/smoke.mjs` ensures (one `smoke` deck) and signs in by minting a session with the stage's `AUTH_SECRET` — never through Cognito's page. It creates one card, logs a retried review against it, and deletes it.
- Secrets (`.env.local`) and `*.db` files are git-ignored — never commit them.
